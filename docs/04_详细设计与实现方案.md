# 个人分布式云盘系统：详细设计与实现方案

本文把架构细化为可实现的模型、接口、状态机和事务边界。字段名是设计基线，最终以数据库迁移、OpenAPI 和 `.proto` 文件为可执行契约。

## 1. 领域模型

### 1.1 服务端核心表

| 表 | 关键字段 | 约束/索引 |
|---|---|---|
| `users` | `id, account, password_hash, status, created_at` | `lower(account)` 唯一；状态不可物理复用 |
| `devices` | `id, user_id, name, platform, public_key, peer_id, status, last_seen_at, version` | `(user_id, public_key)`、`peer_id` 唯一；注销保留审计记录 |
| `sessions` | `id, user_id, device_id, family_id, refresh_hash, expires_at, revoked_at, rotated_from` | refresh hash 唯一；按 user/device 查询 |
| `folders` | `id, user_id, parent_id, name, normalized_name, status, version` | 活跃记录 `(user_id,parent_id,normalized_name)` 唯一 |
| `file_objects` | `id, user_id, sha256, size, mime, chunk_size, chunk_count, status` | `(user_id,sha256,size)` 唯一 |
| `file_entries` | `id, user_id, folder_id, object_id, name, normalized_name, origin_device_id, status, version` | 活跃记录 `(folder_id,normalized_name)` 唯一 |
| `replicas` | `id, object_id, device_id, state, size, verified_at, reported_at, version` | `(object_id,device_id)` 唯一；READY/验证时间索引 |
| `transfer_tasks` | `id, user_id, object_id, target_device_id, reason, state, priority, lease_owner, lease_until, attempt, version` | 活跃任务去重；目标/状态/优先级索引 |
| `transfer_sources` | `task_id, source_device_id, rank, last_error, disabled_at` | `(task_id,source_device_id)` 唯一 |
| `redundancy_policies` | `id, user_id, scope_type, scope_id, desired_replicas, constraints, version` | scope 唯一 |
| `trash_records` | `id, file_entry_id, original_folder_id, original_name, deleted_at, purge_after, status` | file_entry 唯一；purge_after 索引 |
| `tombstones` | `id, user_id, object_id, generation, expires_at, status` | `(object_id,generation)` 唯一 |
| `tombstone_acks` | `tombstone_id, device_id, acked_at, result` | 复合主键 |
| `idempotency_keys` | `user_id, key, request_hash, status, response_code, response_body, expires_at` | `(user_id,key)` 主键 |
| `account_events` | `user_id, seq, type, entity_id, entity_version, payload, created_at` | `(user_id,seq)` 主键；seq 单调 |

`normalized_name` 使用 Unicode NFC 后的名称。V1 逻辑目录区分大小写，因此不做 `casefold`；Windows 落盘前额外检查本地大小写冲突和保留名。

### 1.2 Agent SQLite

| 表 | 用途 |
|---|---|
| `local_objects` | Hash、大小、对象相对路径、状态、最后验证时间、inode/file-id 快照 |
| `local_replicas` | 服务端 replica ID、对象、上报状态、待上报结果 |
| `local_transfers` | task、状态、候选源、临时路径、总块数、已完成字节、错误 |
| `transfer_chunks` | `(task_id, chunk_index)`、offset、size、expected_hash、state |
| `catalog_cache` | 服务端目录/文件的只读缓存和 entity version |
| `outgoing_ops` | 本地导入登记和任务结果等等待服务端确认的幂等操作 |
| `sync_state` | 账号、last_applied_seq、快照版本 |
| `settings` | 存储根、并发、带宽、网络/电池策略，不保存明文秘密 |
| `lan_files` | LAN V1 逻辑条目、对象引用、显示名、`active/trashed/purging`、删除与到期时间 |

SQLite 开启 WAL、foreign keys 和 busy timeout；所有写经单一 store 组件串行化，避免多个 goroutine 任意持有写事务。

`lan_files` 的活动名称按 `(owner_user_id, normalized_name)` 检查冲突。迁移前已经存在的重名条目不得被静默覆盖或删除；后续创建、重命名和恢复均拒绝产生新的活动冲突。

## 2. 状态机

### 2.1 本地对象

```text
ABSENT -> IMPORTING/DOWNLOADING -> VERIFYING -> READY
                         |              |
                         v              v
                       FAILED        QUARANTINED
READY -> DELETING -> ABSENT
READY -> MISSING/CORRUPT -> VERIFYING or ABSENT
```

- `IMPORTING/DOWNLOADING` 必须对应 `.part` 和进度记录。
- `READY` 只能由 storage 组件在完整 Hash 成功后设置。
- `CORRUPT` 不直接删除，先隔离并上报；用户或 GC 策略决定清理。

### 2.2 服务端 Replica

```text
PENDING -> READY -> MISSING | CORRUPT | DELETING -> DELETED
```

`QUEUED/TRANSFERRING/VERIFYING` 属于 TransferTask，不放进 Replica 状态，避免“尚不存在的副本”与“任务进度”混淆。

### 2.3 TransferTask

```text
QUEUED -> ASSIGNED -> DISCOVERING -> CONNECTING -> TRANSFERRING -> VERIFYING -> COMPLETED
              |            |             |              |
              +------------+-------------+--------------+-> WAITING_SOURCE
              +-------------------------------------------> RETRY_WAIT
ANY_NONTERMINAL -> PAUSED | CANCELED
RETRY_WAIT/WAITING_SOURCE -> QUEUED
```

- 终态：`COMPLETED, CANCELED, FAILED_PERMANENT`。
- `attempt` 只在重新领取完整尝试时加一；同一连接内重拨不加。
- 每次更新使用 `(id, version)`；旧 Agent 的迟到结果不会覆盖新状态。

### 2.4 文件删除

```text
ACTIVE -> TRASHED -> PURGING -> PURGED
   ^          |
   +--RESTORED+
```

恢复只允许 `TRASHED`；进入 `PURGING` 后返回冲突。`PURGED` 是逻辑文件终态，对象是否 GC 由引用和 tombstone 独立决定。

## 3. 控制面 API 约定

### 3.1 通用头与响应

- `Authorization: Bearer <access-token>`
- 写操作：`Idempotency-Key: <UUID>`
- 乐观并发：`If-Match: "<version>"`
- 追踪：`traceparent`；响应 `X-Request-ID`
- 分页：`?cursor=<opaque>&limit=100`，limit 最大 500。

错误格式：

```json
{
  "error": {
    "code": "NAME_CONFLICT",
    "message": "目录中已存在同名项目",
    "request_id": "req_...",
    "details": {"conflicting_entry_id": "..."}
  }
}
```

### 3.3 导入事务

请求含 `folder_id, name, sha256, size, mime, chunk_size, device_id, local_verified_at`。

同一事务内：

1. 锁定并验证幂等键；校验设备属于当前账号且活跃。
2. 锁定目标 folder，规范化名称，由唯一约束检测冲突。
3. `INSERT ... ON CONFLICT` 获取 FileObject；若同 Hash 但 size 不同则拒绝。
4. 创建 FileEntry；upsert 当前设备 Replica 为 READY。
5. 写 `FILE_IMPORTED` account event 和幂等响应。
6. 提交后才通知 WebSocket；通知失败不回滚业务事务。

## 4. P2P 传输协议

协议 ID：`/sharedisk/object-transfer/1.0.0`。

### 4.1 握手

1. libp2p 建立加密、认证连接。
2. 目标发送 `TransferOpen{protocol_version, task_id, ticket, object_hash, requested_chunks}`。
3. 源验证签名、期限、账号、source/target device、PeerID、公钥绑定、object 和允许范围。
4. 源返回 `TransferAccept{chunk_size, total_size, manifest_digest, available_chunks}` 或稳定拒绝码。
5. 双方确认参数后才发送数据 frame。

票据默认 5 分钟，只允许指定目标从指定源读取指定对象；已开始的连接可在票据到期后完成，断线重连必须重新取票。

### 4.2 数据帧

- `ChunkRequest{index}`：允许流水线，但未完成请求数不超过 `parallel_chunks`。
- `ChunkData{index, offset, bytes, chunk_hash}`：frame 最大 `chunk_size + overhead`。
- `ChunkAck{index}`：目标完成 Hash 和持久化进度后发送。
- `TransferClose{status}`：不替代完整对象校验。

V1 采用固定 4 MiB chunk。manifest 由 `object_hash, size, chunk_size, ordered chunk hashes` 计算摘要；切换源时必须与已接受 manifest 一致，否则拒绝该源。

### 4.3 接收持久化顺序

1. 校验 index/offset/size 和 chunk hash。
2. `WriteAt` 到预分配 `.part` 文件。
3. 按批次同步数据后，在 SQLite 事务中标记 chunk 完成。
4. 全块完成后流式计算完整 SHA-256。
5. 同步文件和父目录，原子 rename 到对象路径。
6. SQLite 设置 local object READY，再幂等上报服务端。

崩溃最多导致最近未提交批次重新下载，不能导致未校验文件变为 READY。

## 5. 源选择与路径策略

候选源先做硬过滤：同账号、Replica READY、设备 ONLINE、未注销、票据可签发、manifest 一致。再排序：

```text
path rank: LAN(0) < DIRECT_WAN(1) < RELAY(2)
score = path_rank_weight
      + recent_failure_penalty
      + active_load_penalty
      + latency_penalty
      - observed_throughput_bonus
```

切源触发：连接丢失、连续块超时、完整性错误或源主动拒绝。使用指数退避但优先尝试尚未失败的其他源；同一源失败达到阈值后冷却。排序必须注入确定性 tie-break（device ID）以便测试。

## 6. 调度与冗余

### 6.1 任务领取

- worker/Agent 仅领取 `target_device_id=自身` 且可执行的任务。
- 数据库用 `FOR UPDATE SKIP LOCKED` 选取有限批次，设置 `lease_owner/lease_until` 后立即提交。
- 执行期间周期续租；完成更新要求 lease owner 和 version 匹配。
- 租约过期只允许重新入队，不自动认为原任务失败；迟到结果由幂等结果接口判定。

### 6.2 冗余协调

每个相关对象串行计算：

1. 锁定 object；统计非删除中的 READY 副本和活跃复制任务。
2. 若 `ready + inflight >= desired`，不创建任务。
3. 过滤目标：无 READY 副本、opt-in、空间阈值、网络/电池策略、未注销。
4. 按容量、稳定在线、网络、设备优先级、负载排序，device ID 稳定打破平局。
5. 创建所需数量任务；活跃任务唯一约束防止重复。

若副本数下降则标记 `DEGRADED` 并生成修复候选；没有目标时保持降级并告警，不无限创建失败任务。

## 7. 回收站、Tombstone 与 GC

### 7.1 进入回收站

锁 FileEntry，改为 TRASHED，写 TrashRecord 和事件；Replica 保持，避免恢复时重传。

### 7.2 到期清理

1. 领取到期 TrashRecord，状态改 PURGING。
2. 若还有其他 ACTIVE/TRASHED FileEntry 引用对象，只清理逻辑记录。
3. 无引用时创建新 generation Tombstone，向所有未注销且声明该对象的设备发删除任务。
4. Agent 删除本地对象后回 ACK；找不到对象也以 `ALREADY_ABSENT` 成功确认。
5. 所有相关活跃设备确认，或设备之后被注销，服务端可把 Replica 标 DELETED。
6. Tombstone 至少保留 30 天；设备上报旧 READY generation 时，服务端返回删除指令而不是恢复引用。

## 8. 同步与冲突

- `account_events.seq` 由账号级计数器在业务事务内分配。
- 单个事件包含 entity type/id/version 和最小变更；敏感字段不进入通用 payload。
- Agent 按 seq 串行应用到 catalog cache；若遇到 gap，停止推进并重新请求。
- 游标早于保留窗口时下载分页 snapshot；snapshot 带 `base_seq`，完成后再应用增量。
- V1 不支持离线目录修改，因此不存在多主目录合并；本地待登记导入若命名冲突，由用户选择新名。

## 9. 平台实现

### 9.1 Windows/Linux

- Agent 独立 daemon；桌面 GUI 和 CLI 经权限受限本地 IPC 调用。
- Windows 原子替换、文件占用、路径大小写和保留名由 Windows adapter 处理。
- Linux 提供 systemd user service；存储根和 SQLite 不建议放 NFS/SMB。

### 9.2 Android

- 用户导入/导出通过 Storage Access Framework；内部受管对象放 app-private storage 或用户授权目录。
- 用户发起的大文件传输优先采用 User-Initiated Data Transfer；延迟型同步使用 WorkManager；需要本地设备持续连接时评估合适的 foreground service type。
- 所有长任务显示系统可见通知和取消入口；不得承诺从任意后台状态即时启动。
- Go 核心暴露窄接口给原生桥接，不把 Android Context 传入领域包。
- Stage 0 必须用当前目标 API 真机验证；验证不通过时采用 Kotlin UI/service + Go mobile library，而不是削弱后台正确性。

## 10. 配置默认值

| 配置 | 默认 | 边界 |
|---|---:|---|
| `chunk_size` | 4 MiB | V1 固定；协议协商必须一致 |
| `parallel_chunks` | 4 | 1..16 |
| `max_active_transfers` | 3 | 按设备配置 |
| `ticket_ttl` | 5 min | 1..15 min |
| `heartbeat_interval` | 20 s | 服务端离线阈值至少 3 个周期 |
| `task_lease` | 60 s | 续租间隔不超过 1/3 lease |
| `trash_retention` | 7 days | 产品固定语义 |
| `tombstone_retention` | 30 days | 可延长，不得低于活跃设备离线策略 |
| `min_free_space` | 5 GiB | 同时保留剩余文件大小安全余量 |
| `event_retention` | 30 days | 超窗使用 snapshot |
| `shutdown_timeout` | 30 s | 小于容器停止宽限期；server/worker 分阶段退出 |
| `healthcheck_timeout` | 2 s | 单项依赖检查有界，不堆积探针请求 |

配置加载顺序：编译默认 < 配置文件 < 环境变量 < 命令行；启动输出有效配置的非敏感摘要，非法配置立即失败。

服务端容器只允许“编译默认 < 环境变量/非机密配置文件 < 命令行”的非交互式加载，不把宿主机个人配置带入镜像。所有敏感项提供 `*_FILE` 形式，文件内容覆盖同名直接环境变量；同时提供两种形式时启动失败，避免来源不明确。

## 11. 服务端容器运行契约

### 11.1 进程与文件系统

| 容器 | 入口 | 可写路径 | 持久卷 | 退出语义 |
|---|---|---|---|---|
| `control-server` | `/app/control-server serve` | 受限 `/tmp` | 无 | 停止接入，等待在途 HTTP/WebSocket，关闭数据库池 |
| `control-worker` | `/app/control-worker run` | 受限 `/tmp` | 无 | 停止领取，取消可取消任务，等待/释放租约 |
| `db-migrate` | `/app/db-migrate up` | 无 | 无 | advisory lock 下前向迁移；成功 0，失败非 0 |
| `relay-bootstrap` | `/app/relay-bootstrap run` | 受限 `/tmp` | 无 | 停止新流，等待现有流至宽限期 |
| `postgres` | 官方入口 | 数据目录 | `postgres_data` | 由数据库自身完成一致关闭 |

前三个应用镜像来自同一源码提交但使用独立 final target。应用容器根文件系统只读，使用固定非零 UID/GID；迁移文件在构建时进入迁移镜像，不从可变宿主目录注入。server/worker/relay 不得访问 Agent 的 SQLite、对象目录或宿主机 Docker API。

### 11.2 启动与健康状态

```text
postgres healthy
       |
       v
db-migrate completed successfully
       |
       +------> control-server ready
       +------> control-worker ready
```

`control-server healthcheck --url=http://127.0.0.1:8080/livez` 作为容器内静态探针入口，不依赖 shell、curl 或 wget。`/readyz` 返回数据库和 schema compatibility 的分项结果；worker 提供等价的进程/ready 探针或由独立健康子命令检查内部循环。不可重试的配置或迁移错误直接非零退出；数据库短暂不可用时服务保持 not ready，并以有界退避恢复。

### 11.3 服务端配置契约

| 环境变量 | 适用容器 | 语义 |
|---|---|---|
| `SHARE_DISK_SERVER_HOST=0.0.0.0` | server | 容器内监听地址 |
| `SHARE_DISK_SERVER_PORT=8080` | server | 容器端口；公网发布由反向代理决定 |
| `SHARE_DISK_POSTGRESQL_URL_FILE=/run/secrets/postgresql_url` | server/worker/migrate | PostgreSQL DSN secret 文件；生产必须启用 TLS 参数 |
| `SHARE_DISK_LOG_FORMAT=json` | 全部应用 | stdout 结构化日志 |
| `SHARE_DISK_LOG_OUTPUT=stdout` | 全部应用 | 禁止生产写容器日志文件 |
| `SHARE_DISK_SHUTDOWN_TIMEOUT=30s` | server/worker/relay | 应用清理上限，必须小于 Compose `stop_grace_period` |
| `SHARE_DISK_MIGRATIONS_DIR=/app/migrations/postgres` | migrate | 镜像内只读迁移资产 |

镜像元数据必须包含 OCI `source`、`revision`、`version`、`created` 标签。Compose 中数据库只连接内部网络，应用只消费 secret，不在命令行或健康输出中展开 DSN。

## 12. 测试实现矩阵

| 层 | 必测内容 | 真实依赖 |
|---|---|---|
| Domain | 状态机、路径、幂等、冗余选择、GC 可达性 | 无 |
| Store | 迁移、唯一约束、锁、租约、event seq | PostgreSQL/SQLite |
| Agent | 崩溃恢复、磁盘满、原子落盘、扫描修复 | 临时真实文件系统 |
| Protocol | 票据、frame 限制、chunk/完整 Hash、兼容性 | 真实 libp2p stream |
| Integration | 导入、同步、下载、推送、切源、删除 | server + 2/3 Agent |
| Network | LAN、不同 NAT、Relay、路径切换 | 独立网络 namespace/真实外网 |
| Platform | daemon、命名管道、SAF、后台通知 | Windows/Linux/Android 真机 |
| Performance | 1/10 GiB、有界内存、Relay 成本、并发 | 固定硬件和网络参数 |
| Container | 镜像构建、非 root/只读、探针、SIGTERM、重建、迁移门禁、卷恢复 | Docker Engine + Compose + PostgreSQL |

## 13. 实现原则

先固定领域状态、存储事务和协议契约，再实现 transport/UI。任何 UI 操作都调用同一应用服务；任何通知都能通过权威状态补拉；任何外部写都能幂等重放；任何 READY 结论都有实际 Hash 校验证据。

服务器实现还必须满足：同一镜像在不同环境只因外部配置而变化；删除并重建应用容器不改变权威状态；迁移、启动、健康、停止和回滚均有明确可测试的进程边界。
